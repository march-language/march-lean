## Global Constraints

- A0's Lean checker is a **verdict pass-through only** — it must NOT inspect
  `"diagnostics"` or `"module"` at all. It reads `"format_version"` and
  `"verdict"` and nothing else. (A1/A2 will consume `"module"` — don't build
  that now, don't leave TODOs implying it's half-done.)
- Verdict contract (from the parent plan §5, do not deviate): exit
  `0`=accept, `1`=reject, `2`=skip (unmodeled construct — A0 never produces
  this, since it doesn't look at the AST; reserve it, don't implement a skip
  path that can trigger), `3`=internal error (malformed JSON, missing/wrong
  `format_version`, missing/invalid `verdict` field).
- `Lean.Data.Json` (Lean 4's own built-in JSON parser, part of every Lean 4
  toolchain — confirmed importable via plain `import Lean.Data.Json` with
  `#eval`/`lean --run`, no lakefile dependency needed) is the JSON library to
  use. Do NOT add a Mathlib dependency for this — the current
  `lakefile.toml` has none, and A0 doesn't need one; keep it that way so CI
  stays fast (no Mathlib cache required for this milestone).
- `format_version` must be checked and must equal `1` (JSON number); a
  mismatch is an error (exit 3), not silently ignored — this is the format's
  future-proofing mechanism per the parent plan.
- The harness (Task 3) is intentionally dependency-light: POSIX shell
  (`bash`), standard Unix tools. `jq` is acceptable if used (assume present —
  GitHub Actions `ubuntu-latest` ships `jq`), but don't require anything more
  exotic.

## Task 1: `MarchLean/Json.lean` — verdict parser

**Files:** new file `MarchLean/Json.lean`.

**Steps:**

1. `import Lean.Data.Json` at the top.
2. Define `inductive Verdict where | accept | reject deriving DecidableEq, Repr`.
3. Define `def parseVerdict (input : String) : Except String Verdict` that:
   - Parses `input` with `Lean.Json.parse` (returns `Except String Json`);
     propagate its error message on failure (prefix with something like
     `"invalid JSON: "` for a clearer error).
   - Looks up the `"format_version"` field (`Json.getObjValAs?` or manual
     `Json.getObjVal?` + pattern match); if missing or not equal to the
     number `1`, return `Except.error` with a message naming what was found
     (e.g. `s!"unsupported format_version: {v}"` or `"missing format_version"`).
   - Looks up the `"verdict"` field as a string; if missing or not one of
     `"accept"`/`"reject"` exactly, return `Except.error` with a message
     naming the offending value.
   - On success, return `Except.ok .accept` or `Except.ok .reject`
     accordingly.
   - Do NOT touch `"diagnostics"` or `"module"` — don't even look them up.

**Verification:**
- Write a handful of `#eval` sanity checks at the bottom of the file (or in a
  scratch file you delete before finishing — your call, but show your work
  in the report) covering: valid accept, valid reject, missing
  `format_version`, wrong `format_version` (e.g. `2`), malformed JSON,
  missing `verdict` field, `verdict` with an unexpected string value (e.g.
  `"maybe"`). Confirm each produces the expected `Except.ok`/`Except.error`.
- `lake build` succeeds (run `export PATH="$PATH:/Users/80197052/.elan/bin"`
  first if not already on PATH this session).

   ```lean

     let stdin ← IO.getStdin
     let input ← stdin.readToEnd
   ```

## Task 3: Conformance harness script

**Depends on:** Task 2, and the `march`-repo `--emit-core-ast` work (see
Global Constraints — you'll need a freshly built `march` binary with that
flag; build it yourself from
`/Users/80197052/code/march/.claude/worktrees/emit-core-ast-a0` if it isn't
already built there).

**Files:** new `scripts/conformance-harness.sh`.

**Steps:**

1. Script takes three inputs (support both env vars and flags, your choice,
   but document whichever you pick in a `--help`/usage comment):
   `MARCH_BIN` (path to the `march` executable), `CORPUS_DIR` (path to
   `specs/lang/types`, i.e. the directory containing `accept/` and `reject/`),
   `MARCH_LEAN_CHECK_BIN` (path to the built `march-lean-check` executable,
   e.g. from `lake exe march-lean-check` or the raw `.lake/build/bin/...`
   path — pick whichever is more robust to invoke from a script; `lake exe`
   re-triggers a build check every time which may be slower in a tight loop
   over 168 files, consider resolving the raw binary path once up front).
2. For each `*.march` file under `$CORPUS_DIR/accept/` and
   `$CORPUS_DIR/reject/`:
   - Run `"$MARCH_BIN" --check "$f"`; capture its exit code. Exit `0` →
     `march_verdict=accept`; nonzero → `march_verdict=reject`. (Confirm this
     is actually `--check`'s convention by testing it directly before relying
     on it — don't assume without checking.)
   - Run `"$MARCH_BIN" --emit-core-ast "$f" | "$MARCH_LEAN_CHECK_BIN"`;
     capture the pipeline's exit code (the `march-lean-check` side, i.e.
     `${PIPESTATUS[1]}` in bash — NOT the `march` side). Map `0→accept`,
     `1→reject`, `2→skip`, `3→error`, anything else → treat as `error` too
     (defensive).
   - Classify: if `lean_verdict` is `error` → record as ERROR (always a
     FAIL). Else if `lean_verdict` is `skip` → record as SKIP (never counted
     as a match, always logged loudly, not itself a FAIL for A0's purposes —
     though A0 should never actually produce skips since Lean doesn't look at
     the AST; if you see one, that's itself worth flagging prominently as
     unexpected). Else if `march_verdict != lean_verdict` → record as
     MISMATCH (FAIL). Else → MATCH.
   - Optional but cheap, do it if straightforward: also extract the
     `"verdict"` field from the `--emit-core-ast` JSON output itself (e.g.
     via `jq -r .verdict` or a `grep`/`sed` one-liner) and cross-check it
     equals `march_verdict` from `--check` — if march's own two flags
     disagree with each other, that's a march-side bug worth surfacing
     distinctly from a Lean mismatch. Label this category separately
     (e.g. `MARCH_SELF_INCONSISTENT`) if you add it; don't conflate it with
     MISMATCH.
3. Print a summary: total files run, counts per category, and the list of
   filenames for every non-MATCH category (MISMATCH/ERROR/SKIP/and the
   optional self-inconsistency category if added).
4. Exit nonzero iff any MISMATCH or ERROR occurred (SKIP alone, in A0, would
   be unexpected but per the parent plan's contract still shouldn't silently
   pass as a match — decide and document whether SKIP fails the run for A0;
   the parent plan says "never let skip masquerade as agreement" which is
   about counting, not necessarily about failing the build — a reasonable
   A0 reading is SKIP is impossible by construction here, so make the exit
   code nonzero on ERROR/MISMATCH, and also nonzero if SKIP ever appears
   since that would indicate this task's own assumptions are wrong).

**Verification:**
- Build fresh `march` (from the `emit-core-ast-a0` worktree, after that
  work lands) and `march-lean-check` binaries as described above.
- Run the harness over the real corpus (`specs/lang/types` from the `march`
  worktree) and confirm it reports all MATCH (168 non-INDEX files, all
  passing through as verdict-echo since A0's Lean side just parrots march's
  own verdict — there should be zero mismatches by construction, since
  Lean's checker at A0 always agrees with the JSON's `verdict` field, and
  that field is defined to equal `--check`'s own verdict).
- **Forced-mismatch check (this is A0's stated acceptance criterion — do not
  skip this):** temporarily and reversibly break the agreement — e.g. patch
  a throwaway copy of `MarchLeanCheck.lean` (or add a `--force-reject <file>`
  test hook, your call on the cleanest way) so it returns the wrong verdict
  for exactly one corpus file, rebuild, rerun the harness, and confirm it
  reports exactly one MISMATCH and exits nonzero. Then revert the temporary
  change, rebuild, and rerun to confirm it's back to all-MATCH before
  finishing. Report the before/after output in your report file.
